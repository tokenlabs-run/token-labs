# Aggregated GLM and Qwen on the Sparks

The maintenance migration on 2026-09-30 replaces disaggregated GLM with one
independent vLLM worker per Spark. The user explicitly authorized the outage
and removal of the old GLM deployment. This exception applies to this migration;
future production changes follow MODEL_ROLLOUT_RUNBOOK.md.

| Node | Served model ID | Native context limit |
| --- | --- | --- |
| spark-01 | `glm-4.7-flash` | 202752 |
| spark-02 | `nvidia/Qwen3.6-35B-A3B-NVFP4` | 262144 |

Context includes input and output tokens. These are the pinned configurations'
native limits, without RoPE extrapolation. Each worker uses tensor parallelism 1
and at most four active sequences. Four simultaneous maximum-length requests
are not a capacity guarantee. Both run as the image's non-root user.

## Deployment sources

- `glm-4.7-flash/plain-vllm/aggregated.yaml`
- `qwen3.6-35b-a3b-nvfp4/plain-vllm/nvidia-aggregated.yaml`
- `../platform/gateway/aigatewayroute-models.yaml`, generated by
  `scripts/common/gen_aigwroute.py`
- `../platform/gateway/model-agent-apis.yaml`

The model revisions and runtime image are pinned. The runtime is vLLM 0.28.0
from the existing custom Dynamo image, launched directly with `vllm serve`.
No Dynamo frontend, KV connector, or separate prefill worker is used.
Qwen uses NVIDIA's checkpoint with the Marlin MoE backend and FP8 KV cache.
GLM keeps its original checkpoint and default cache precision.

Do not apply pod-template changes to a publicly selected worker in place.
The RollingUpdate strategy is not a substitute for the rollout runbook.
The retired Dynamo manifest has zero replicas and must not be used as the
active deployment source.

The model aggregator discovers Services labeled `token-labs/model=true`.
It refreshes without a restart. Generate and review the direct gateway routes
only after both workers pass diagnostic tests:

```sh
python3 scripts/common/gen_aigwroute.py --discovery live
kubectl apply -f deploy/platform/gateway/aigatewayroute-models.yaml
kubectl apply -f deploy/platform/gateway/model-agent-apis.yaml
```

## Public API checks

Both models use `https://api.tokenlabs.run/v1/chat/completions`.

```sh
curl --fail-with-body https://api.tokenlabs.run/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"glm-4.7-flash","messages":[{"role":"user","content":"Write a Python function that adds two integers."}],"max_tokens":512,"chat_template_kwargs":{"enable_thinking":false}}'

curl --fail-with-body https://api.tokenlabs.run/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"nvidia/Qwen3.6-35B-A3B-NVFP4","messages":[{"role":"user","content":"Write a Python function that adds two integers."}],"max_tokens":512,"chat_template_kwargs":{"enable_thinking":false}}'
```

The dedicated native API prefixes are `/models/glm` and `/models/qwen`.
They preserve vLLM's Responses and Anthropic Messages payloads without AI
Gateway protocol conversion. They inherit gateway-level policies; the
route-specific extension policy follows the existing model-list policy.
The existing `/openrouter/v1` proxy continues to require its provider key.

Run the curl-based verifier for each native API prefix:

```sh
python3 scripts/serving/check_agent_apis.py \
  --base-url https://api.tokenlabs.run/models/glm --model glm-4.7-flash
python3 scripts/serving/check_agent_apis.py \
  --base-url https://api.tokenlabs.run/models/qwen \
  --model nvidia/Qwen3.6-35B-A3B-NVFP4
```

This checks completion, streaming, and structured tool calls across Chat
Completions, Responses, and Messages. It does not certify coding quality or
full-context throughput. Set `TOKENLABS_API_KEY` if authentication is required.

## Harness connection values

| Harness | GLM base URL | Qwen base URL |
| --- | --- | --- |
| Codex Responses provider | `https://api.tokenlabs.run/models/glm/v1` | `https://api.tokenlabs.run/models/qwen/v1` |
| Claude Code `ANTHROPIC_BASE_URL` | `https://api.tokenlabs.run/models/glm` | `https://api.tokenlabs.run/models/qwen` |

Use the exact served model IDs in the first table. Configure Codex's custom
provider with `wire_api = "responses"`, `supports_websockets = false`, and
`requires_openai_auth = false`. Keep the configured context window within the
server limit and reserve space for generated tokens. Claude Code can select
the model with `--model`; background model aliases must also point to a served
model if enabled. Native API compatibility alone does not prove every harness
feature, such as compaction or custom tool formats, is supported.

Use the checked-in harness smoke command to exercise the actual installed CLI:

```sh
scripts/serving/check_harness_client.sh codex \
  https://api.tokenlabs.run/models/qwen nvidia/Qwen3.6-35B-A3B-NVFP4
scripts/serving/check_harness_client.sh claude \
  https://api.tokenlabs.run/models/glm glm-4.7-flash
```

For Codex, the script sets `model_context_window` to the model's native limit
and `model_auto_compact_token_limit` to 90% of that value. The installed Codex
can warn that custom model metadata is unavailable and fall back to generic
metadata. Claude Code may independently report a 200K context window. Server
context limits do not automatically override client metadata.

These text-only CLI checks do not exercise file editing, automatic compaction,
or every tool format. API tool-call checks are separate. Cold prompts near the
context limit can take minutes on a Spark; the client check allows ten minutes.
