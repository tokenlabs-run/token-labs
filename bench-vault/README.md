# bench-vault

A small, boring, durable place to keep LLM inference benchmark results —
so that "what did we test, with what profile, and what happened" is always
answerable months later.

## The rule that makes this work

**Files are the truth; MLflow is the index.**
Every run is archived immutably as raw harness JSON + a manifest.
MLflow makes runs searchable and comparable. If MLflow dies, the archive
still stands. If a harness changes its metric definitions (it will —
GenAI-Perf → AIPerf changed what "TTFT" means), the manifest records the
harness name, harness version, and metric schema, so historical numbers
are never silently compared across definitions.

## Layout

```
bench-vault/
  results/
    2026-10-26/
      qwen3-32b__gb10__vllm-0.11.0__fp8__tp2__c32__isl1024-osl256/
        manifest.yaml     # the profile: engine, hardware, config, harness
        raw.json          # untouched harness output
        summary.json      # flattened percentiles (generated by log_run.py)
  scripts/
    run_bench.sh        # run a benchmark, then archive + log it
    log_run.py          # ingest harness JSON -> archive + MLflow
  docker-compose.yaml   # MLflow tracking server (SQLite + local artifacts)
```

Run directory name = `model__gpu__engine-version__quant__tpN__cCONC__islX-oslY`.
Ugly on purpose: the name alone tells you what the run was.

## Quick start

```bash
# 1. Start the tracking server (or skip MLflow entirely — see below)
docker compose up -d            # MLflow UI on http://localhost:5000

# 2. Run a benchmark and log it in one step
./scripts/run_bench.sh \
  --harness vllm --endpoint http://localhost:8000 \
  --model Qwen/Qwen3-32B --gpu GB10 --quant fp8 --tp 2 \
  --concurrency 32 --isl 1024 --osl 256

# or log an existing result file
python scripts/log_run.py --result ~/bench-output.json --harness vllm \
  --model Qwen/Qwen3-32B --gpu GB10 --engine-version 0.11.0 \
  --quant fp8 --tp 2 --concurrency 32 --isl 1024 --osl 256

# No MLflow server handy? --dry-run writes summary.json + prints the record.
python scripts/log_run.py --result ~/bench-output.json --dry-run ...
```

## What gets stored per run

| Kind | Examples |
|---|---|
| Params (the profile) | engine + version, harness + version, model, GPU, quantization, TP/PP/DP/EP, max_num_seqs, gpu_memory_utilization, concurrency, ISL/OSL, arrival pattern |
| Metrics | TTFT / ITL / E2E p50·p90·p99, output tok/s, req/s, goodput if SLOs given |
| Artifacts | raw harness JSON, manifest.yaml, summary.json |

## Supported harness outputs

- **vLLM** `vllm bench serve --save-result` JSON (per-request `ttfts`, `itls`, `e2els` arrays → percentiles computed here)
- **GuideLLM** `benchmarks.json` (percentiles extracted from its summary metrics)
- Anything else: percentiles are computed from any top-level per-request
  latency arrays found; the raw file is always archived regardless.

## Placement (decided Oct 26, 2026)

- **This code lives in the token-labs repo** (`bench-vault/`) — benchmarks are
  product data and version with the serving stack they measure.
- **The MLflow server is deployed from the homelab repo**
  (`infrastructure/mlflow/`, Flux/kustomize) — it's a platform service like
  Prometheus/Grafana. Point `MLFLOW_TRACKING_URI` at it.
- **Public-repo guardrail:** token-labs is public. Token Slab results are
  fine to commit; anything from the hosted pilot goes in `results-private/`
  (git-ignored) — infra details for the pilot are not published.

## Notes for the Token Slab / DGX Spark setup

- GB10 is ARM64 — the MLflow compose file uses the official image; if your
  registry mirror lacks an ARM build, run MLflow directly on the controller
  node instead: `pip install mlflow && mlflow server --host 0.0.0.0`.
- In the Kubernetes/GitOps setup, point `MLFLOW_TRACKING_URI` at the
  in-cluster service and mount `results/` on the same PVC your benchmark
  jobs already write to.
